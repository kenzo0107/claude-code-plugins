# レビュー知見 (learnings) のフォーマット

実際に受けたPRレビューの指摘を一般化して蓄積するディレクトリ。
`/learn-review` が追記し、`/self-review` が照合に使う。Gitが原本
(参考: https://engineering.mercari.com/blog/entry/20260630-b22667b4d6/ )。

## ファイル構成

| ファイル | 対象 | ルールIDプレフィックス |
|---|---|---|
| `general.md` | 言語非依存の知見 | `GEN-` |
| `go.md` | Go | `GO-` |
| `python.md` | Python | `PY-` |
| `ruby.md` | Ruby | `RB-` |
| `terraform.md` | Terraform | `TF-` |
| `typescript.md` | TypeScript/JavaScript | `TS-` |

対象言語のファイルが無ければ新規作成する。上記以外の言語も同じ命名規則で追加してよい。

## エントリのフォーマット

```markdown
## GEN-001: エラーを握りつぶさず、ログ出力または伝播する
- 分類: correctness | security | testing | design | readability | operations
- 登録日: YYYY-MM-DD
- 出典: <PRのURL> (社外秘の場合はリポジトリ名のみ)

ルールの説明を1〜3行で。なぜ問題なのか(Why)を必ず含める。

悪い例:
(コード例。固有名詞はマスキング済みであること)

良い例:
(コード例)
```

- ルールIDはファイル内で連番。欠番が出ても詰めない
- 「悪い例 / 良い例」は無くてもよいが、あると照合精度が上がる

## 蓄積時のルール

1. **一般化する**: 特定のPR・特定の関数にしか当てはまらない指摘は登録しない。
   「次回以降の別の変更でも同じ指摘を受けうるか」で判断する
2. **マスキングする**: 個人名は記録しない。プロダクト名・内部システム名・URL・
   識別子は先頭数文字だけ残してマスキングする (例: `med****`)
3. **重複させない**: 追加前に既存エントリを確認し、類似ルールがあれば新規追加でなく
   既存エントリを更新・強化する
4. **鮮度を保つ**: 誤りだと分かったルール・前提が変わったルールは削除または修正する
