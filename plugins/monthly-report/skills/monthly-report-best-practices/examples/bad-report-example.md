# よくある誤りと修正例

このファイルは、月報でよくある誤りとその修正例を示しています。

## 誤り1: 活動ログになっている

### ❌ 悪い例

```markdown
## ① 今月のメインスコープ

- PR #123をマージした
- PR #456をレビューした
- ミーティングに参加した
- バグを修正した
```

### 問題点

- **何をしたかだけ**: 行動の羅列で、価値が見えない
- **チケット番号なし**: どのプロジェクトか不明
- **完了状態なし**: 結果がわからない
- **ミーティング参加**: これ自体は成果ではない

### ✅ 修正例

```markdown
## ① 今月のメインスコープ

- **基盤移行後の旧処理整理（TECH-1234）**: 完了
  - システムの旧処理を4タスクに分けて整理
  - 19 PRに分割して段階的に実施

- **求人APIリニューアル（PROD-5678）**: 本番リリース完了
  - Gateway廃止のブロッカーを解消
  - 新エンドポイント `GET /api/v1/main-app/offers` 実装
```

### 修正のポイント

- ✅ プロジェクト名を明記
- ✅ チケット番号を追加
- ✅ 完了状態を明示
- ✅ 何をどう実現したかを説明

## 誤り2: 曖昧な表現だらけ

### ❌ 悪い例

```markdown
## ② Valueの証明

### Q: 品質を改善した

コードをリファクタリングして品質を改善しました。
いくつかのバグを修正し、テストも追加しました。
レビューもたくさん実施して、チーム全体の品質向上に貢献しました。
```

### 問題点

- **「改善した」**: 何をどれだけ改善したか不明
- **「いくつかの」**: 具体的な数が不明
- **「たくさん」**: 定量化されていない
- **「品質向上に貢献」**: 結果が曖昧

### ✅ 修正例

```markdown
## ② Valueの証明

### Q: 基盤移行後の旧処理を体系的に整理・削除

削除対象の影響範囲（DB連携・外部API呼び出し・関連サービス）を事前に調査した上で、
安全に除去できる順序を設計し、19 PR（main-app 13件・framework 4件・
core-api 1件・data-jobs 1件）に分割して段階的に実施。

技術的負債の解消であると同時に、後続開発のリスク低減にも直結する整理であった。
月間20+件のコードレビューを実施し、5つのリポジトリで潜在的なバグを事前に検出・修正。
```

### 修正のポイント

- ✅ **具体的な数値**: 19 PR、4リポジトリ、20+レビュー
- ✅ **プロセスの説明**: 「影響範囲を調査」「順序を設計」「段階的に実施」
- ✅ **価値の明示**: 「技術的負債解消」「リスク低減」
- ✅ **結果の定量化**: 「5つのリポジトリ」「潜在的バグを検出」

## 誤り3: エビデンスが整理されていない

### ❌ 悪い例

```markdown
## ④ エビデンス

- https://github.com/org/repo/pull/123
- https://github.com/org/repo/pull/456
- https://github.com/org/repo/pull/789
- https://github.com/org/repo2/pull/111
- https://github.com/org/repo2/pull/222
- https://github.com/org/repo3/pull/333
- https://github.com/org/repo3/pull/444
- https://github.com/org/repo3/pull/555
```

### 問題点

- **整理されていない**: どのPRがどのプロジェクトか不明
- **説明がない**: PRの内容が分からない
- **グループ化なし**: 関連性が見えない
- **重み付けなし**: どれが重要か分からない

### ✅ 修正例

```markdown
## ④ エビデンス

### 基盤移行後の旧処理整理 (70%)

#### main-app (13件)
- [#39656: 旧処理の削除](https://github.com/org/repo/pull/39656)
- [#39675: 旧API呼び出しの整理](https://github.com/org/repo/pull/39675)
- [#39688: 依存関係の解消](https://github.com/org/repo/pull/39688)
...

#### framework (4件)
- [#4935: 旧認証処理の削除](https://github.com/org/repo2/pull/4935)
- [#4936: レガシーキャッシュの整理](https://github.com/org/repo2/pull/4936)
...

### 求人APIリニューアル (30%)

- [career-rails #2716: 新エンドポイント実装](https://github.com/org/repo3/pull/2716)
- [career-rails #2728: キャッシュ制御追加](https://github.com/org/repo3/pull/2728)
```

### 修正のポイント

- ✅ **プロジェクト別にグループ化**: 基盤整理、APIリニューアル
- ✅ **重み付け**: 作業量の割合を明示（70%, 30%）
- ✅ **リポジトリごとに整理**: main-app、frameworkなど
- ✅ **PR説明**: 各PRが何をしたかが分かる

## 誤り4: 進化・非停滞が抽象的

### ❌ 悪い例

```markdown
## ③ 進化・非停滞の証明

- 新しい技術を学びました
- Reactを使ってフロントエンド開発をしました
- いろいろなツールを活用しました
- 開発速度が上がりました
```

### 問題点

- **「学びました」だけ**: 実践した証拠がない
- **「使いました」**: 使用≠成長
- **「いろいろな」**: 具体性ゼロ
- **「上がりました」**: どれだけ、どう上がったか不明

### ✅ 修正例

```markdown
## ③ 進化・非停滞の証明

- **KMP（Kotlin Multiplatform）でのクロスプラットフォーム開発**:
  記事カテゴリ選択画面で共有モジュール→Android→iOSの全レイヤーを一人で実装。
  Compose Multiplatformのボトムシート・スクリム・ナビゲーション・iOS委譲コールバックなどの
  実践的知見を蓄積。従来のiOS/Android個別開発と比較してコード共有率60%達成。

- **インフラ/DevOps領域への対応拡大**:
  GitHub Actions非推奨対応、GitHub Apps Token移行、Ruby更新、Dependabot設定など、
  CI/CD領域でアプリ単位ではなくリポジトリ横断の改善をリード。8リポジトリで一括対応を実現。

- **複数リポジトリを横断した自走力**:
  main-app・framework・core-api・data-jobsと規約・構成の
  異なる4リポジトリにわたる作業を一人で完遂した。各リポジトリの構造・CIルールへの適応コストが
  前月比で50%削減。
```

### 修正のポイント

- ✅ **実践の証拠**: 「全レイヤーを一人で実装」
- ✅ **定量化**: 「コード共有率60%」「8リポジトリ」「適応コスト50%削減」
- ✅ **新規性の明示**: KMP（初めて）、インフラ/DevOps（領域拡大）
- ✅ **前月との比較**: 「前月比で50%削減」

## 誤り5: Q/L/Dの分類が不適切

### ❌ 悪い例

```markdown
## ② Valueの証明

### Q: 新機能を実装した

ユーザーからの要望で検索機能を実装しました。
高速で動作するように工夫しました。
```

### 問題点

- **Qではなくd**: ユーザー要望への対応はDelivery
- **「工夫」が曖昧**: 何をどう工夫したか不明
- **結果の記載なし**: どれだけ速くなったか不明

### ✅ 修正例

```markdown
## ② Valueの証明

### D: ユーザー要望への迅速対応

CS経由でエスカレーションされた検索機能の要望（月間30件の問い合わせ）に対応。
PdMと仕様を調整し、2週間で本番リリース完了。検索速度3秒→0.5秒に改善し、
ユーザー離脱率を20%削減（アナリティクス計測）。

### L: 検索基盤の再設計による将来的効率化

ElasticsearchからOpenSearchへの移行と並行して、検索クエリの共通化基盤を構築。
今後の新規検索機能追加時の実装工数を70%削減可能な設計に。
```

### 修正のポイント

- ✅ **適切なカテゴリ**: ユーザー要望=D、効率化基盤=L
- ✅ **数値的証拠**: 3秒→0.5秒、離脱率20%削減、工数70%削減
- ✅ **ビジネス価値**: CS問い合わせ削減、ユーザー離脱削減
- ✅ **将来価値**: 今後の効率化を明示

## よくある禁止表現リスト

### 曖昧な動詞

| ❌ 避けるべき | ✅ 具体的な表現 |
|------------|--------------|
| 改善した | API応答速度を30%改善（200ms→140ms） |
| 調整した | 認証フローを再設計し、セキュリティ要件を満たすよう変更 |
| 対応した | CS問い合わせから根本原因を特定し、修正PRをマージ |
| 修正した | 決済フローのバグ（影響ユーザー200名）を修正 |
| 実装した | OAuth2.0認証機能（MP-1234）を本番リリース完了 |
| 追加した | E2Eテストを30ケース追加し、カバレッジ60%→85%に向上 |
| 削除した | 旧処理を19 PRに分割して段階的に削除、技術的負債を解消 |
| 検討した | パフォーマンス改善策を検討し、ElasticsearchからOpenSearchへの移行を決定 |

### 曖昧な量詞

| ❌ 避けるべき | ✅ 具体的な表現 |
|------------|--------------|
| 多くの | 50+ PR、20+レビュー |
| いくつかの | 3つのリポジトリ、5箇所の修正 |
| たくさんの | 月間30件の問い合わせ |
| 複数の | 8リポジトリで一括対応 |
| 様々な | GitHub Actions、Ruby、Dependabotの3領域 |

### 曖昧な結果表現

| ❌ 避けるべき | ✅ 具体的な表現 |
|------------|--------------|
| 品質向上 | テストカバレッジ60%→85%、バグ検出5件 |
| 効率化 | PR作成時間を15分→5分に短縮、月間10時間削減 |
| パフォーマンス改善 | API応答速度30%改善（200ms→140ms） |
| ユーザー体験向上 | 離脱率20%削減、満足度スコア3.5→4.2 |

## 自己チェックリスト

月報を書いたら、以下をチェック：

### 構造チェック

- [ ] メインスコープにチケット番号・完了状態がある
- [ ] Q/L/Dのいずれかに記載がある（全て必須ではない）
- [ ] 進化・非停滞の証明がある
- [ ] エビデンスが整理されている

### 具体性チェック

- [ ] 10個以上の具体的な数値がある
- [ ] 影響範囲（リポジトリ数、ユーザー数、チーム）を明示
- [ ] PRの数、レビューの数を記載
- [ ] 時間軸（いつ、どのくらいの期間）が明確

### 曖昧表現チェック

- [ ] 「改善」「調整」「対応」を使っていない
- [ ] 「多くの」「いくつかの」を使っていない
- [ ] 「品質向上」「効率化」だけで終わっていない
- [ ] すべての動詞に具体的な結果がついている

### エビデンスチェック

- [ ] PRリンクがカテゴリごとに整理
- [ ] 各PRに簡潔な説明が付いている
- [ ] 重み付け（%）または優先度を記載
- [ ] リポジトリ別にグループ化

### 成長チェック

- [ ] 「学んだ」だけでなく「実践した」証拠がある
- [ ] 新しい技術・領域への挑戦を示している
- [ ] 前月との差分が明確
- [ ] 能力拡大の定量化（速度向上、範囲拡大など）

## 修正演習

### 演習1

以下の文章を修正してください：

```
バグを修正して、品質を改善しました。
```

<details>
<summary>修正例を見る</summary>

```
決済フローのバグ（影響ユーザー200名）を修正。根本原因（DB トランザクション処理の競合）を特定し、
排他制御を追加することで再発を防止。本番影響前に対処完了。
```

**改善点:**
- バグの種類を明示（決済フロー）
- 影響範囲を定量化（200名）
- 根本原因を説明
- 対策内容を具体化（排他制御追加）
- タイミングを明記（本番影響前）
</details>

### 演習2

以下の文章を修正してください：

```
新しいツールを使って作業を効率化しました。
```

<details>

Claude Codeのスラッシュコマンド（日報・月報自動生成、Compose移行コマンド）を導入し、

## まとめ

月報で避けるべき5大誤り：

1. **活動ログ化**: 何をしたかだけでなく、何を実現したかを書く
2. **曖昧表現**: 「改善」「調整」「対応」ではなく、具体的な行動と結果を書く
3. **エビデンス羅列**: PRリンクをカテゴリ別・リポジトリ別に整理
4. **抽象的成長**: 「学んだ」ではなく「実践した」証拠を示す
5. **Q/L/D誤分類**: 価値の種類を正しく理解して分類

これらを意識すれば、評価者に伝わる月報が書けます。
